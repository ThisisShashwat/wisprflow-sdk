# WisprFlow SDK Technical Documentation

## Overview

This project is an unofficial Python SDK that interfaces directly with Wispr Flow's backend transcription infrastructure. Rather than automating the desktop application, the SDK reproduces the network requests performed by the official client and exposes them through a clean Python API.

The implementation was developed through analysis of the Wispr Flow desktop application and its communication protocols.

---

# Architecture

The SDK communicates directly with Wispr's backend services.

```text
┌─────────────┐
│ Python App  │
└──────┬──────┘
       │
       ▼
┌─────────────────┐
│ WisprFlow SDK   │
└──────┬──────────┘
       │
       ├── Reads session.json
       ├── Reads wispr_runtime.json
       │
       ▼
┌─────────────────┐
│ gRPC Backend    │
└─────────────────┘
```

Unlike the desktop application, no GUI, Electron runtime, browser automation, Flask server, or local HTTP bridge is required.

---

# Authentication

The SDK does not implement its own login flow.

Authentication is delegated entirely to the official Wispr Flow desktop application.

The SDK reuses the authenticated session stored locally by Wispr.

## session.json

Location:

```text
%APPDATA%\Wispr Flow\session.json
```

This file is automatically created and maintained by the official desktop application.

The SDK extracts:

* Access token
* User identifier (derived from token payload)

The access token is attached to all gRPC and REST requests.

Example flow:

```text
session.json
    │
    ▼
access_token
    │
    ▼
Authorization: Bearer <token>
```

If the user is not logged into Wispr Flow, the SDK cannot authenticate.

# Runtime Configuration

In addition to authentication, the SDK requires runtime connection metadata used internally by Wispr.

These values include:

* Model ID
* Environment
* Backend Host
* Baseten API Key

The official client does not expose these values directly.

---

# Runtime Patch

The repository includes a PowerShell patch script:

```text
patch_wispr.ps1
```

The purpose of this patch is to expose runtime configuration already present within the installed Wispr Flow application.

## What the Patch Does

1. Locates the newest installed Wispr Flow version.
2. Terminates running Wispr processes.
3. Creates a backup of `app.asar`.
4. Extracts the Electron application.
5. Patches internal JavaScript.
6. Repackages the application.
7. Restores the modified application.

The patch injects logic that writes runtime connection information to:

```text
%LOCALAPPDATA%\WisprFlow\wispr_runtime.json
```

after the next transcription request.

---

# wispr_runtime.json

Generated by:

```text
patch_wispr.ps1
```

Typical contents:

```json
{
  "modelId": "...",
  "environment": "...",
  "url": "...",
  "apiKey": "..."
}
```

The SDK reads these values at runtime and uses them to construct the gRPC connection.

Without this file, the SDK cannot determine:

* Which model endpoint to use
* Which environment is active
* Which host to connect to
* Which Baseten API key to provide

---

# Required Files

The SDK depends on two external files:

```text
%APPDATA%\Wispr Flow\session.json
%LOCALAPPDATA%\WisprFlow\wispr_runtime.json
```

Both must be present.

| File               | Source                   |
| ------------------ | ------------------------ |
| session.json       | Generated by Wispr login |
| wispr_runtime.json | Generated by patch       |

No additional credential files are required.

# Audio Processing Pipeline

Input audio can be supplied in any format supported by FFmpeg.

Supported examples:

```text
wav
mp3
m4a
ogg
webm
aac
flac
```

Pipeline:

```text
Audio File
    │
    ▼
FFmpeg Conversion
    │
    ▼
16 kHz
Mono
PCM16 WAV
    │
    ▼
gRPC Upload
    │
    ▼
Transcript Result
```

The SDK automatically converts audio when necessary.

# gRPC Protocol

Communication with Wispr's transcription backend occurs over gRPC.

The SDK manually constructs protobuf payloads and therefore does not require generated protobuf classes.

Benefits:

* No `.proto` files required
* No `protoc` dependency
* Smaller installation footprint
* Easier reverse-engineering workflow

The SDK reproduces:

* Initialization packets
* Context packets
* Audio packets
* Commit packets

used by the desktop client.

Examples:

```python
before_text=""

selected_text=""

content_html=""

```

```python
screen_ax=[]
```

These values are encoded into the same context structures used by the official client.

# Transcription Modes

## Standard Transcription

```python
result = client.transcribe("audio.wav")
```

Returns:

* Raw transcript
* Formatted transcript
* Final transcript
* HTML result
* Metadata

---

## Command Mode

```python
result = client.command(...)
```

Workflow:

```text
Audio
  │
  ▼
Transcription
  │
  ▼
Command Routing API
  │
  ▼
Transformed Text
```

Used for commands such as:

```text
make this formal
rewrite this
summarize this
```

```text
      ▼

      │
      ▼

      ▼
```

* Personal dictionary
* Starred dictionary

* Snippets
* Cleanup level
* Writing styles
* Signature settings

Configuration is persisted to:

```text
wispr_config.json
```

---

# Security Considerations

Never publish:

```text
session.json
wispr_runtime.json
wispr_config.json
```

These files may contain:

* Access tokens
* API keys
* User information
* Personal vocabulary
* Custom replacements

Recommended:

```gitignore
session.json
wispr_runtime.json
wispr_config.json
*.wav
```

---

# Compatibility

The SDK depends on implementation details extracted from the Wispr desktop client.

Future Wispr updates may change:

* Authentication storage
* Runtime configuration
* gRPC message format
* API endpoints
* Model identifiers

Changes to these components may require updates to the SDK.
